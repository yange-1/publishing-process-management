# 出版流程项目管理平台 - 项目需求文档

## 1. 项目背景

目前单位出版业务中，每年约有200本图书进入出版流程。

一本书从编辑加工到最终出版，需要经历不同的校对流程，例如：

- 初审
- 一校
- 二校
- 三校
- 加校
- 核红

由于出版项目数量较多，且不同图书经历的流程节点存在差异，目前主要依靠人工沟通的方式了解项目进度。

实际工作中存在以下问题：

1. 无法快速查看一本书当前处于哪个流程阶段；
2. 无法直观看到全部出版项目的推进情况；
3. 编辑人员无法及时了解项目当前进展；
4. 校对管理人员无法及时发现长期停留在某一流程节点的项目；
5. 需要通过反复询问确认项目状态，增加沟通成本。

---

# 2. 项目目标

建设一个轻量化内部出版流程管理平台，实现：

- 出版项目统一管理；
- 出版流程节点可视化；
- 快速查看项目当前进度；
- 减少人工沟通和重复确认；
- 自动发现长期滞留项目；
- 为后续出版数据统计分析提供基础。

---

# 3. 第一阶段建设目标（MVP）

第一阶段不建设复杂企业级管理系统，而是建设一个简单、稳定、易使用的内部工具。

重点解决：

> “一本书现在进行到哪一步？哪些项目停滞？哪些项目需要关注？”

---

# 3.1 来稿与任务发布

“来稿”不由任何人手工填写。社内责任编辑在系统中发布一条校对任务，即代表该校次书稿已经进入校对部门。

责任编辑点击“发布校对任务”的时间，由系统自动作为：

- 本校次校对任务发布时间；
- 本校次来稿时间；
- 本校次滞留计时起点；
- 本校次进入书稿仓库的时间。

责任编辑只填写必要业务内容：书名、当前校次、稿件星级、必要说明。责任编辑、实际发布操作人、发布时间和来稿时间均由系统根据登录账号与当前时间自动填写，不手工录入。

责任编辑发布任务后，任务自动进入书稿仓库，状态自动变为“待确认收稿”，页面显示“新任务”提醒。第一版提醒采用系统页面内的数字、标记或醒目提示，不要求短信或邮件通知。

社内校对主管具有最高权限，可以代责任编辑发布。代发时责任编辑仍记录具体书稿的责任编辑，实际操作人记录社内校对主管，系统标记为代操作。

---

# 3.2 出版流程节点管理

不同图书根据实际出版情况选择需要经历的流程节点。

系统支持以下流程节点：

- 初审；
- 一校；
- 二校；
- 三校；
- 加校；
- 核红。

不同项目不要求经历全部流程。

例如：

- 部分项目只需要初审；
- 部分项目需要经历一校、二校；
- 部分项目可能直接进入核红；
- 部分项目需要完整经历多个校次流程。

系统根据项目实际情况展示对应流程。

每个流程节点，第一版即记录：

- 节点状态（未开始、进行中或已完成）；
- 开始时间；
- 完成时间。

通过流程记录，可以查看：

- 已完成节点；
- 当前进行节点；
- 后续待处理节点。

---

# 3.3 任务状态管理

任务状态统一为：

- 待确认收稿（PENDING_CONFIRMATION）；
- 已确认待开始（READY_TO_START）；
- 进行中（IN_PROGRESS）；
- 已结束（COMPLETED）；
- 已取消（CANCELLED，仅供超级管理员纠错使用）。

页面归类：

- 书稿仓库：待确认收稿 + 已确认待开始；
- 生产线：进行中；
- 已完成：已结束；
- 已取消不进入正常生产统计，但保留历史记录。

“滞留”用于表示任务自发布（来稿）起停留时间过长，需要管理人员关注，由系统自动计算，不由工作人员手工选择。

第一阶段不设置预计完成时间。

原因：

出版流程受作者修改、编辑调整、校样反馈等多种因素影响，预计完成时间可能造成不必要的管理压力和沟通矛盾。

# 3.4 出版流程可视化管理看板

为了方便校对管理人员快速掌握当前出版项目情况，系统首页采用可视化看板方式展示正在处理中的书稿。

## 3.4.1 项目展示方式

项目不采用单纯文字列表展示，而采用卡片式展示。

每个书稿项目以独立卡片形式显示：

包括：

- 稿件等级；
- 书名；
- 责任编辑；
- 校对负责人；
- 当前流程阶段；
- 当前状态；
- 来稿时间。

示例：

⭐⭐⭐《某某研究》

当前阶段：

二校

责任编辑：

XXX

校对负责人：

XXX

收到时间：

2026-08-01

状态：

进行中

---

## 3.4.2 流程节点颜色展示

不同出版流程阶段采用不同颜色进行区分。

第一阶段设置：

| 流程阶段 | 展示颜色 |
| -------- | -------- |
| 初审     | 蓝色     |
| 一校     | 绿色     |
| 二校     | 黄色     |
| 三校     | 橙色     |
| 加校     | 紫色     |
| 核红     | 红色     |

通过颜色区分，使管理人员能够快速判断当前项目分布情况。

---

## 3.4.3 稿件等级展示

根据出版工作实际情况，设置稿件重要程度。

第一阶段设置三个等级：

| 等级     | 展示方式 | 处理阈值 |
| -------- | -------- | -------- |
| 普通稿件 | 无星标识 | 30天     |
| 急稿     | ⭐⭐     | 15天     |
| 重要急稿 | ⭐⭐⭐   | 7天      |

急稿和重要急稿在页面中通过星级进行突出展示。

---

## 3.4.4 项目排序规则

首页项目按照优先级进行排序。

排序原则：

第一优先级：

稿件等级。

排序：

⭐⭐⭐重要急稿

↓

⭐⭐急稿

↓

普通稿件

第二优先级：

来稿时间。

同等级项目：

按照来稿时间排序。

收到时间越早的项目越靠前。

---

# 3.5 项目处理周期与滞留预警机制

## 3.5.1 计时起点

第一阶段项目处理时间从：

> 本校次来稿时间（即责任编辑发布任务时间，系统自动生成）

开始计算。

不以：

- 外校公司主管确认收稿时间；
- 校对人员开始工作时间；

作为主要计时依据。

原因：

管理人员需要关注的是：

> 书稿进入校对部门后是否长期未完成。

---

## 3.5.2 第一阶段阈值规则

根据稿件重要程度设置处理阈值。

普通稿件：

30天

急稿：

15天

重要急稿：

7天

初审阶段：

统一设置90天。

第一阶段暂不考虑：

- 不同字数；
- 不同图书类型；
- 更复杂业务规则。

后续根据实际运行数据逐步优化。

---

## 3.5.3 滞留项目展示

超过处理阈值的项目：

同时存在于两个区域：

第一：

正常项目时间序列中。

第二：

独立的“滞留预警区域”。

滞留区域采用醒目的红色展示。

显示内容：

- 书名；
- 稿件等级；
- 当前阶段；
- 已处理时间；
- 超出阈值时间。

示例：

⚠️ 滞留项目

⭐⭐⭐《某某研究》

当前阶段：

二校

已处理：15天

阈值：7天

超过：8天

# 4. 用户角色与任务流程

系统采用四步极简流程，并遵循开放查看原则。

## 4.1 四步流程

1. 社内责任编辑点击“发布校对任务”；
2. 外校公司主管点击一次“确认收稿”；
3. 任意空闲校对人员点击“开始校对”；
4. 当前校对人员点击“结束校对”。

没有分发、领取登记、返回责任编辑等中间步骤。

## 4.2 社内责任编辑

- 发布校对任务；
- 查看、搜索所有书稿；
- 查看自己书稿的当前状态和完整校对历史；
- 可取消自己发布的、尚未进入生产线的任务。

## 4.3 外校公司主管

- 查看全部书稿；
- 对“待确认收稿”的任务执行一次“确认收稿”；
- 不负责在平台内分发书稿，不填写领取时间。

## 4.4 校对人员

- 查看全部书稿，包括与自己无关的书稿；
- 空闲时可对“已确认待开始”的任务点击“开始校对”，系统自动把当前账号记为校对负责人并记录开始时间；
- 同一校对人员同一时段只能加工一本书；
- 当前校对人员点击“结束校对”，系统自动记录结束人和结束时间。

## 4.5 社内校对主管（超级管理员）

- 最高权限，可执行全部角色的业务操作；
- 可管理账号、纠正错误状态、代替其他角色处理特殊情况；
- 所有代操作和纠错进入审计日志，记录实际操作账号、时间、代操作角色、原因及状态变化；
- 管理范围覆盖社内及外校公司及其账号。

## 4.6 开放查看原则

所有已登录用户都可以查看和搜索全部书稿（状态、校次、是否进入生产线、校对历史、滞留信息）。角色权限主要限制“谁能执行什么操作”，不限制普通书稿的查看范围。MVP 阶段不做复杂的外校公司数据隔离，公司信息仍保留用于账号归属、操作记录和未来统计。

## 4.7 极简操作与自动填写

发布、确认收稿、开始校对、结束校对四个操作均尽量“一次点击”完成。系统自动填写：当前操作账号、操作人姓名、所属公司或部门、操作时间、当前任务状态、当前负责人、状态变化记录。普通用户不得手工填写操作人、负责人或业务时间。

## 4.8 取消规则

原则上只有“待确认收稿”或“已确认待开始”任务可取消。责任编辑可取消自己发布的未开始任务；已开始任务如需纠错，由社内校对主管处理并写入审计日志。取消必须记录取消人、取消时间和原因。

## 4.9 并发与责任

1. “确认收稿”幂等，重复点击不产生重复事件；
2. “开始校对”原子条件更新：只有待开始可被开始，两名校对人员同时点击只允许一人成功，已有进行中任务的校对人员不能开始第二本；
3. “结束校对”只能由当前任务的校对人员或超级管理员执行；
4. 普通用户不能修改已经生成的历史事件。

## 4.10 操作责任记录

每个任务保留只追加、不覆盖的事件记录，事件类型为：TASK_PUBLISHED、RECEIPT_CONFIRMED、TASK_STARTED、TASK_COMPLETED、TASK_CANCELLED。每条事件至少记录：任务、事件类型、实际操作账号、操作时间、是否代操作、代操作角色、状态变化、必要备注。

## 4.11 搜索结果与校对历史

搜索支持按书名、责任编辑等条件查询。书稿历史至少显示：发布人和发布时间、确认收稿人和确认时间、开始人/实际校对人员和开始时间、结束人和结束时间、当前状态、是否滞留、历次校对任务及各校次流程记录。不记录“返回责任编辑”。

## 4.12 总控预警

首页最多展示 20 条滞留任务，包含书稿仓库滞留和生产线滞留，每条显示所在区域；仓库中的普通稿即使排序靠后，只要滞留，也必须进入总控预警；超过 20 条时显示“查看全部滞留任务”。

## 4.13 未来统计数据

第一版不制作复杂统计页面，但操作记录必须真实保存。未来通过记录计算：每位编辑发布的任务数量、每个校次的来稿数量、书稿仓库等待时间、生产线加工时间、每位校对人员完成的任务数量、各校次平均耗时、滞留数量、不同流程节点的瓶颈。

# 5. 使用规模

预计：

- 年项目数量：约200本；
- 年流程节点：约1000个左右；
- 使用人员：单位内部工作人员。

系统规模：

> 小型内部业务管理工具

# 6. 技术要求

第一阶段要求：

- 支持电脑浏览器访问；
- 操作简单；
- 界面清晰；
- 便于后续扩展。

当前技术方案：

前端：

- Next.js；
- React；
- TypeScript；
- Tailwind CSS。

开发辅助：

- Visual Studio Code；
- Claude Code AI 编程助手。

---

# 7. 项目开发原则

遵循：

1. 优先解决实际业务问题；
2. 第一阶段控制开发范围；
3. 保持系统简单稳定；
4. 为后续功能扩展保留空间；
5. 根据实际使用反馈持续优化。

# 9. 后续扩展方向

在第一阶段基础上，可进一步增加：

## 9.1 出版数据统计

例如：

- 年度出版项目数量统计；
- 已完成项目数量统计；
- 进行中项目统计；
- 滞留项目统计。

## 9.2 流程效率分析

例如：

- 各校次平均耗时统计；
- 不同流程节点耗时分析；
- 发现出版流程瓶颈。

## 9.3 工作量分析

例如：

- 不同责任编辑项目数量统计；
- 不同校对负责人工作量统计。

## 9.4 智能提醒

未来可扩展：

- 消息通知；
- 自动提醒；
- 异常项目预测。

## 项目定位

本项目第一阶段定位为出版流程管理工具。

通过对校对流程进行数字化管理，解决当前出版业务中的进度查询、流程追踪和滞留发现问题。

未来可根据业务发展，逐步扩展为出版业务数字化平台中的流程管理模块，并与其他出版业务系统进行数据对接。
