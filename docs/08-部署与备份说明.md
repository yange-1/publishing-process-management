# 出版校对流程管理平台 —— 部署与备份说明

版本：V1.0
日期：2026年8月22日

---

## 1. 正式数据库默认位置

正式数据库默认位于项目目录下：

```
data/publishing-process.db
```

数据库路径可通过环境变量 `DATABASE_PATH` 覆盖（备份与恢复脚本同样遵守该变量）。数据库采用 SQLite，连接时开启 `journal_mode = WAL`。

---

## 2. 创建备份的命令

```bash
npm run db:backup
```

该命令调用 `scripts/db-backup.mjs`，使用 better-sqlite3 的在线备份 API（`db.backup()`）生成安全快照，并对备份库自动执行完整性检查与六表行数比对，全部一致才提示“备份成功”。

---

## 3. 备份文件默认位置与命名规则

- 默认备份目录：`data/backups/`
- 命名规则：`publishing-process-<YYYYMMDD>-<HHMMSS>.db`（本地时间），例如 `publishing-process-20260822-153000.db`
- 同一秒内重复执行会自动追加序号，避免覆盖已有备份

可通过环境变量 `BACKUP_DIR` 覆盖备份目录。

---

## 4. 恢复验证命令

```bash
npm run db:restore-check -- <备份文件路径>
```

例如：

```bash
npm run db:restore-check -- data/backups/publishing-process-20260822-153000.db
```

该命令把指定备份复制到系统临时目录，只读校验其完整性并比对六张表行数，全部一致才提示“恢复验证通过”。

---

## 5. 恢复验证使用系统临时目录，绝不覆盖正式数据库

恢复验证脚本会在系统临时目录（`os.tmpdir()`）中创建独立临时文件夹，把备份复制进去后再做只读校验，验证结束即删除该临时副本。整个过程**不覆盖、不替换、不重命名、不删除正式数据库**。脚本会拒绝把正式数据库路径当作验证对象。

---

## 6. 为什么 WAL 模式下不能随意直接复制正在运行的 .db 文件

数据库以 WAL（Write-Ahead Logging）模式运行。写入会先进入 `-wal` 日志文件，再在 checkpoint 时合并回主 `.db` 文件。若直接复制主 `.db` 文件而忽略 `-wal`/`-shm`，可能得到一个**不完整、不一致的副本**，恢复后数据缺失或损坏。

因此备份必须使用 SQLite 的在线备份 API（`db.backup()`），它能在数据库运行期间生成一致快照；或先停止服务、让 WAL 完成 checkpoint 后再复制。**恢复验证同样只对备份产物操作，不直接复制运行中的正式库。**

---

## 7. 备份目录不进入 Git

`data/backups/` 已加入 `.gitignore`，备份文件不会被提交到 Git 仓库。备份属于本机数据，与正式数据库一样只保存在本地受保护位置。

---

## 8. GitHub 不能代替业务数据库备份

GitHub 存放的是**代码**，不是运行数据。正式数据库和备份文件都已被 `.gitignore` 排除、不会被提交。即使代码仓库被完整克隆，也无法恢复业务数据。业务数据的安全只取决于本机的备份与离线存储，GitHub 不具备备份数据的作用。

---

## 9. 本地 data/backups 只能防止误操作，不能防止整块磁盘损坏

`data/backups/` 与正式数据库在同一块磁盘上，只能应对“误删、误改、程序写坏”等逻辑错误。若整块磁盘损坏、失窃或机房故障，本机备份会与正式库一起丢失，因此**不能**作为唯一备份手段。

---

## 10. 后续应把已验证备份复制到独立存储位置

每次 `npm run db:backup` 成功并通过恢复验证后，应将备份文件复制到单位批准的**独立存储**，例如：

- 移动硬盘；
- 内网文件服务器 / NAS；
- 其他已批准的主机。

备份文件的异地副本才是真正的数据安全保障。

---

## 11. 建议的备份频率和保留方式

- 频率：**每完成一个工作日后至少备份一次**；数据变动频繁时可在重要操作后立即备份。
- 保留：本机 `data/backups/` 建议保留最近 7–14 天；异地存储建议至少保留最近 30 天，并保留每月一份的长期备份。
- 每次备份后建议随即执行一次 `db:restore-check`，确认备份可恢复。

---

## 12. 真正恢复正式数据库前必须做到

1. **停止服务**（关闭 `next dev` / `next start`），确保没有连接在写入数据库；
2. **保留故障库副本**：把当前正式 `data/publishing-process.db` 复制到别处留档，绝不先删除；
3. **由管理员人工确认**恢复对象与恢复时点无误；
4. 用备份文件替换正式库后，重新执行 `PRAGMA integrity_check` 与六表行数核对；
5. 确认无误后再重新启动服务。

严禁在服务运行中直接覆盖正式数据库文件。
