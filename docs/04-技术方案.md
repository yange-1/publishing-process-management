# 出版流程项目管理平台 - 技术方案

# 1. 系统建设思路

本项目定位为出版流程管理平台第一阶段建设。

系统通过对出版流程进行数字化管理，实现：

- 出版项目统一管理；
- 流程节点可视化；
- 项目进度实时查看；
- 长期滞留项目发现；
- 出版流程数据沉淀。

第一阶段不建设大型出版业务系统，而是采用模块化设计方式，优先解决当前出版流程管理中的实际问题。

未来系统可逐步扩展为出版社数字化业务平台中的流程管理模块，并与其他出版业务系统进行数据对接。

# 3. 系统功能模块设计

系统主要包括以下模块：

## 3.1 出版任务管理模块

系统以“校次任务”为单位管理出版流程，采用四步极简流程：

- 社内责任编辑发布本校次校对任务（即“来稿”），任务进入待确认收稿；
- 外校公司主管一键“确认收稿”，任务变为待开始；
- 任意空闲校对人员一键“开始校对”，任务进入生产线；
- 当前校对人员一键“结束校对”，任务完成并退出生产线。

任务基础信息包括：

- 书名；
- 责任编辑（任务发布人）；
- 稿件等级；
- 当前阶段；
- 当前状态；
- 来稿时间（系统自动生成）。

支持：

- 发布任务；
- 确认收稿；
- 开始校对；
- 结束校对；
- 取消任务（责任编辑/超级管理员）；
- 查看任务列表与详情；
- 查看校对历史。
- 外校主管首页直接展开“待确认收稿”区域（仅本公司）并可逐条确认；其“已完成任务”点击进入独立分页页面。
- 责任编辑首页按本人维度展示（待确认/生产线/已完成仅本人书稿），部门书稿仓库展示全部 READY_TO_START 并支持按接收外校公司筛选、显示各公司数量。

---

## 3.2 出版流程管理模块

每一本书根据实际情况选择需要经历的流程节点。

流程节点包括：

- 初审；
- 一校；
- 二校；
- 三校；
- 加校；
- 核红。

不同项目不要求经历全部流程。

例如：

- 部分项目只需要初审；
- 部分项目需要经历多个校次；
- 部分项目直接进入核红。

系统根据项目实际情况展示对应流程。

# 4. 数据模型设计

## 4.1. 出版项目对象（BookProject）

第一阶段，一个出版项目代表一本正在处理的书稿。

字段包括：

| 字段              | 说明                         |
| ----------------- | ---------------------------- |
| id                | 任务编号                     |
| bookId            | 所属图书项目                 |
| stage             | 当前校次                     |
| level             | 稿件等级                     |
| status            | 当前状态                     |
| note              | 必要说明                     |
| workWordCount     | 工作字数（发布时填写，正整数，可空） |
| externalConfirmedWordCount | 外校确认字数（确认收稿时可改，可空） |
| editorId          | 责任编辑（任务发布人·责任人）  |
| publisherId       | 实际发布操作人                |
| isProxyPublished  | 是否代发布                   |
| publishedAt       | 发布时间 = 来稿时间 = 滞留起点 |
| confirmerId       | 确认收稿操作人                |
| companyId         | 所属外校公司                 |
| isProxyConfirmed  | 是否代确认                   |
| confirmedAt       | 确认时间                     |
| proofreaderId     | 校对负责人（开始时自动设置）   |
| startedAt         | 开始时间 = 进入生产线时间      |
| finisherId        | 结束操作人                   |
| finishedAt        | 结束时间                     |
| cancelledBy       | 取消人                       |
| cancelledAt       | 取消时间                     |
| cancellationReason| 取消原因                     |

“是否滞留”不落库，读取时按 publishedAt 与阈值实时计算；完整操作历史另存 task_events，超级管理员纠错另存 audit_log。

字数说明：字数按每一次校对任务分别记录（不是一本书所有校次共用），两个字段均为可空整数，单位统一为「字」、只允许正整数。工作字数在发布时填写后不可修改；外校确认字数创建时自动等于工作字数，外校主管确认收稿时可修改（仅限本公司任务），修改前值与修改后值写入 audit_log、变化说明写入 task_events.note。第一阶段只记录字数，不计算单价、金额和校对费。历史正式数据迁移后两个字段保持 NULL（页面显示「未填写」），禁止用 0 或虚构数字填充；数据库升级使用项目现有幂等迁移脚本（scripts/db-migrate.mjs），不会在应用启动时偷偷修改正式数据库。

## 4.3. 第一阶段流程模型

第一阶段记录：

- 当前流程阶段；
- 项目整体状态；
- 来稿时间；
- 每个流程节点的状态（未开始、进行中或已完成）；
- 每个流程节点的开始时间；
- 每个流程节点的完成时间。

流程阶段包括：

- 初审；
- 一校；
- 二校；
- 三校；
- 加校；
- 核红。

每个流程节点的开始时间和完成时间，仅用于工作记录及未来统计，不用于滞留判断。

## 滞留项目单独进入预警区域。

# 5. 滞留提醒规则设计

系统不设置预计完成时间。

原因：

出版流程受到作者修改、编辑调整、校样反馈等多种因素影响，固定预计完成时间可能造成管理压力。

系统采用：

> 根据“本校次来稿时间”起算的处理时长判断项目是否需要关注。

---

## 5.1 稿件等级

第一阶段设置三个等级：

普通稿：

默认校次提醒阈值：

30天

急稿：

默认校次提醒阈值：

15天

重要急稿：

默认校次提醒阈值：

7天

---

## 5.2 流程节点特殊规则

初审阶段：

统一设置：

90天

原因：

初审流程与校对流程不同，通常周期较长。

---

## 5.3 第一阶段提醒逻辑

计时统一从“本校次来稿时间”（即责任编辑发布任务时间）开始计算。

判断：

自来稿时间起的已处理时间 > 对应阈值

则：

项目标记为：

- 需要关注；
- 滞留项目。

管理页面显示：

- 项目名称；
- 当前阶段；
- 来稿时间；
- 停留时间。

---

## 5.4 自动自然语言提醒

达到或超过处理阈值的未完成任务（待确认收稿 / 待开始 / 进行中），在首页「总控预警」任务卡中自动生成一条自然语言提醒；已结束、已取消不生成。

- 触发条件：`已等待天数 >= 阈值天数`，即达到阈值当天或超过阈值；天数由服务器当前日期实时计算，页面每次打开时自动更新。
- 提示语规则（纯函数生成，不含书名与状态——书名已在任务卡顶部展示，避免重复）：
  - 达到阈值当天：`已收稿N天，请尽快处理！`（「已收稿N天」后使用中文逗号）；
  - 超过阈值后：`已收稿N天！请尽快处理！`（「已收稿N天」后使用中文感叹号）。
- 超过阈值的提示继续使用醒目红色；达到阈值当天使用琥珀色。
- 阈值规则复用现有 `overdueThresholdDays`（初审 90 天；非初审普通 30 天、急稿 15 天、重要急稿 7 天），不另写一套规则。
- 不依赖大模型或外部 API；提示语在读取时按访问时间动态生成，不写入数据库，不修改表结构。

# 6. 数据安全设计

出版数据包含未出版书名、编辑信息等业务数据，需要保证数据安全。

第一阶段：

采用以下措施：

1. 使用本地数据库保存业务数据；

2. 定期备份数据库文件；

3. 不将真实业务数据提交到公共代码仓库；

4. AI辅助开发过程中避免输入敏感出版数据。

未来：

可增加：

- 用户登录（内部试用版必要）；
- 角色权限（内部试用版必要）；
- 操作日志；
- 数据服务器部署。

# 9. 第一阶段开发范围

第一阶段重点完成：

- 出版项目管理；
- 流程节点管理；
- 项目状态管理；
- 稿件等级设置；
- 滞留提醒；
- 数据库存储；
- 基础页面展示。

暂不实现：

- 在线稿件编辑；
- 文件管理；
- 多系统数据接口；
- 复杂统计分析。

权限说明：系统采用开放查看原则，所有已登录用户可查看和搜索全部书稿；角色权限主要限制“谁能执行什么操作”。社内责任编辑发布、外校公司主管确认收稿、校对人员开始/结束、社内校对主管为超级管理员。正式多人使用前，简单登录和角色权限是内部试用版的必要功能。演示版仍可使用虚构数据和静态角色展示。

---

# 10. 开发原则

遵循：

1. 优先解决实际业务问题；
2. 保持系统简单稳定；
3. 模块化设计；
4. 为未来扩展预留空间；
5. 根据实际使用反馈持续优化。
