# 出版校对流程管理平台——项目制作框架

版本：V1.0  
日期：2026年8月19日  
适用工具：Visual Studio Code、DeepSeek 大模型、ChatGPT Plus

## 一、先明确最终要做成什么

本项目不是一个“大型出版系统”，而是一个小型内部 Web 管理工具。

第一版只解决三个核心问题：

1. 一本书目前走到哪个校对阶段；
2. 哪些书稿需要优先处理；
3. 哪些书稿已经滞留，需要管理人员关注。

系统建成后，用户通过电脑浏览器访问。业务由四类账号按四步极简流程推进：社内责任编辑发布校对任务（即“来稿”），外校公司主管一键“确认收稿”，校对人员一键“开始校对”，当前校对人员一键“结束校对”；社内校对主管为超级管理员，负责代操作与纠错。

本系统本身不需要接入任何大模型。DeepSeek 和 ChatGPT Plus 是帮助制作系统的工具，不是系统运行所必需的组成部分。即使以后不再使用大模型，已经做好的系统仍然可以正常运行。

## 二、第一版必须保留的业务规则

### 1. 项目基础信息

每条校次任务至少保存：

- 书名；
- 责任编辑（任务发布人）；
- 校对负责人；
- 稿件等级；
- 本校次来稿时间（= 发布时间，系统自动生成）；
- 当前校次；
- 当前状态；
- 确认收稿操作人与确认时间；
- 开始操作人（校对人员）与开始时间（= 进入生产线时间）；
- 结束操作人与结束时间；
- 取消人、取消时间与取消原因；
- 是否滞留（系统计算）；
- 所属外校公司。

### 2. 流程节点

系统支持：

- 初审；
- 一校；
- 二校；
- 三校；
- 加校；
- 核红。

每本书可以选择其中一部分节点，不强制走完全部流程。

每个被选中的节点记录：

- 未开始、进行中或已完成；
- 开始时间；
- 完成时间；
- 节点顺序。

第一版保留“开始校对”和“结束校对”操作，因为这是实际工作流程所需，也能为以后的耗时统计留下可靠数据。

### 3. 滞留判断

滞留计时统一从“本校次来稿时间”（即责任编辑发布任务时间，系统自动生成）开始，不从校对人员点击开始的时间计算。

- 当前阶段是初审：90天；
- 其他阶段的普通稿件：30天；
- 其他阶段的急稿：15天；
- 其他阶段的重要急稿：7天。

“滞留”应由系统自动计算，不由工作人员手工选择。流程状态和滞留标识分开：项目可以处于“进行中”，同时被系统标记为“已滞留”。

### 4. 首页看板（三个管理视角）

首页采用“书稿仓库—生产线—总控预警”三个管理视角，不使用传统表格作为主要展示方式。

1. 书稿仓库：已确认收稿、等待校对人员开始的书稿（待开始 / READY_TO_START），是公共任务池，按星级排序展示。
2. 生产线：已开始、尚未完成的书稿（进行中），同样按星级排序展示。
3. 总控预警：待确认收稿滞留、书稿仓库滞留与生产线滞留，首页最多展示 20 条，超出时显示“查看全部滞留任务”。

外校公司主管的首页额外展开“待确认收稿”区域（统计卡后、书稿仓库前，仅本公司），可直接逐条确认收稿；其“已完成任务”改为点击进入独立分页页面，首页不再展开已完成长列表。

责任编辑的首页按本人维度展示：待确认/生产线/已完成仅统计本人书稿；书稿仓库展示全部 READY_TO_START（可按接收外校公司筛选并显示各公司数量），用于判断承载情况；不展示全部门滞留统计与总控预警。

校对人员、Dominance 的首页保持书稿仓库—生产线—已完成—总控预警的展示。

每条信息展示：星级、书名、当前阶段、责任编辑、校对负责人、来稿时间、当前状态、已等待天数。

排序顺序：

1. 重要急稿；
2. 急稿；
3. 普通稿；
4. 同等级内，来稿时间越早越靠前。

阶段颜色：初审蓝色、一校绿色、二校黄色、三校橙色、加校紫色、核红红色。

滞留项目既保留在原星级序列中，也进入总控预警区域。

### 5. 任务流程（四步极简）

第一版采用四步极简流程，无分发、无领取登记、无返回责任编辑：

- 社内责任编辑：发布本校次校对任务（即“来稿”），任务进入待确认收稿，状态为“待确认收稿”；
- 外校公司主管：对“待确认收稿”任务一键“确认收稿”，状态变为“待开始”，不负责分发、不填领取时间；
- 校对人员：对“待开始”任务一键“开始校对”（从首页书稿仓库或搜索结果），系统自动把当前账号设为校对负责人并记录开始时间，任务进入生产线；
- 当前校对人员：一键“结束校对”，任务完成并退出生产线。

每个动作由系统自动记录操作人和时间：

- 发布 → 发布时间 = 本校次来稿时间 = 滞留计时起点；
- 确认收稿 → 确认操作人、所属外校公司、确认时间；
- 开始 → 开始操作人、开始时间 = 进入生产线时间；
- 结束 → 结束操作人、结束时间 = 本校次完成时间。

“来稿”不由任何人手工填写，所有操作人、负责人和业务时间均由系统根据登录账号与当前时间自动生成。本校次结束后，如有下一校次，由责任编辑再次发布新的校对任务，新任务重新进入待确认收稿并生成新的来稿时间。

取消：原则上只有“待确认收稿”或“待开始”可取消，责任编辑可取消自己发布的未开始任务，超级管理员可处理已开始任务的纠错；取消记录取消人、时间和原因。

### 6. 一个校对人员一条任务

一个校对人员同一时段只能存在一条进行中的校对任务。

校对人员点击“开始校对”时，系统必须原子地检查该人员是否已有进行中的任务；若已有，则阻止开始第二本，并显示其正在加工的书名与当前流程阶段，须等其结束当前任务后才能开始下一本。若两名校对人员同时点击同一“待开始”任务，系统只允许一人成功，另一人得到“该任务已被领取”提示。

## 三、资料中需要统一的两处矛盾

正式开发前，应以本框架为准统一以下内容：

1. 《项目需求》要求第一版记录每个节点的开始和结束时间，《技术方案》又把它写成后续功能。最终决定：第一版记录节点开始和结束时间。
2. 个别技术说明使用“当前节点开始时间”判断滞留，但已确认的业务规则要求从“本校次来稿时间”计时。最终决定：来稿时间用于滞留判断；节点开始和结束时间只用于工作记录和未来统计。

## 四、三种工具怎样分工

| 工具 | 主要职责 | 不应该承担的职责 |
| --- | --- | --- |
| ChatGPT Plus | 保存和梳理需求、拆分任务、审查方案、解释报错、制定测试清单、整理领导汇报材料 | 不把网页对话误当成电脑里的项目代码；不输入真实敏感书稿数据 |
| VS Code | 保存真实项目文件、查看修改、运行系统、查看报错、使用 Git 保存版本 | 它本身不是大模型，也不会自动理解业务需求 |
| DeepSeek | 在 VS Code 中读取当前项目文件，按一次一个小任务生成或修改代码，修复明确报错 | 不要一次把整个系统全部交给它生成；不要允许它在未说明时重做架构 |

最稳妥的配合方式是：

1. 在 ChatGPT Plus 中确定本阶段要做什么和验收标准；
2. 把这一阶段的文档和任务说明交给 VS Code 中的 DeepSeek；
3. DeepSeek 每次只完成一个小任务；
4. 在 VS Code 中实际运行并测试；
5. 把运行结果或报错交给 DeepSeek修复；
6. 阶段完成后，把结果和截图交给 ChatGPT Plus复核并更新文档。

ChatGPT 项目可以保存共享的文件、说明和多次对话，但网页版 ChatGPT 项目不等于电脑上的 VS Code 文件夹。需要让 DeepSeek 修改的最新文档，仍应放在电脑项目的 docs 文件夹内。每次文档发生重要变化，要同步两边的正式版本，避免两个版本互相冲突。

## 五、建议采用“两道交付门”

### 交付门 A：10天演示版 MVP

目标：用模拟数据向领导展示完整业务闭环。

包含：

- 卡片式首页；
- 新建、查看、修改和删除项目；
- 自选流程节点；
- 开始和结束节点；
- 自动进入下一节点；
- 稿件等级和排序；
- 滞留判断与红色预警；
- SQLite 数据保存；
- 数据备份和恢复验证；
- 测试记录和使用说明。

演示版只使用虚构书名、虚构人员和模拟日期，不录入真实未出版数据。

### 交付门 B：单位内部试用版

目标：让编辑和校对人员通过单位内部网络正式使用。

在演示版基础上补充：

- 用户登录；
- 角色权限；
- 编辑只读查询；
- 校对主管可以修改流程；
- 单位内网服务器或长期在线电脑部署；
- 正式备份制度；
- 操作日志；
- 小范围试运行。

第一阶段文档原本把权限放到以后，这是可以接受的演示版范围；但如果要让多名编辑查看真实数据，登录和基本权限必须在正式试用前完成。

## 六、系统如何摆放

开发和演示时，系统可以运行在自己的电脑上，SQLite 数据库也保存在该项目的受保护数据目录中。

正式多人使用时，不能把数据库分别放到每位编辑的电脑上。正确方式是：

1. 在单位内网的一台长期在线电脑或服务器上运行一套 Web 系统；
2. SQLite 数据库只保存在这台主机上；
3. 编辑和校对人员通过浏览器访问同一个内部网址；
4. 只有服务器端应用读写数据库；
5. 定期把数据库备份到单位批准的位置。

当前每年约200本书、约1000个流程节点，集中式 SQLite 足以支持演示和小范围试用。若以后并发用户、数据量或系统对接明显增加，再迁移到 PostgreSQL。

## 八、10天制作路线

### 第1天：锁定需求和检查现有项目

工作：

- 把本框架同步到电脑项目的 docs 文件夹；
- 统一前述两处矛盾；
- 让 DeepSeek 只读取和分析现有项目，不修改文件；
- 确认现有项目是否能正常启动；
- 确认 Git 仓库是私有仓库；
- 建立第一个开发前版本记录。

交给 DeepSeek 的任务说明：

> 请先只分析，不修改任何文件。读取 docs 中的项目需求、开发计划、技术方案和项目制作框架，检查当前项目目录、技术栈和已完成功能。请输出：现有内容、缺失内容、可能冲突、最小的下一步任务。不要生成整个系统，不要更换已经确定的技术栈。

完成标准：现有项目状态已经说清，项目能启动，下一步只有一个明确任务。

### 第2天：完成静态首页和视觉规则

工作：

- 先用模拟项目卡片做首页；
- 完成星级、阶段颜色、等待天数和红色预警区域；
- 按等级和收到时间展示正确顺序；
- 此时先不连接真实数据库。

完成标准：领导不需要解释就能看懂哪个项目重要、哪个阶段、是否滞留。

### 第3天：建立数据结构和本地保存

工作：

- 建立项目数据和流程节点数据；
- 接入 SQLite；
- 准备少量虚构测试数据；
- 确认关闭并重新启动后数据仍然存在。

完成标准：项目和流程记录可以持久保存，数据库文件不进入公开仓库。

### 第4天：完成项目新建、查看和修改

工作：

- 新建项目；
- 选择稿件等级；
- 选择实际需要的流程节点；
- 填写收到时间、责任编辑和校对负责人；
- 查看详情和修改项目。

完成标准：能建立一条完整且字段正确的测试项目。

### 第5天：完成流程开始和结束

工作：

- 未开始的节点可以点击开始；
- 开始后记录开始时间；
- 进行中的节点可以点击结束；
- 结束后记录完成时间；
- 自动把下一选定节点设为当前节点；
- 最后一个节点结束后，项目变为已完成。

完成标准：一个项目能够从第一个节点一直操作到最终完成，时间记录完整。

### 第6天：完成滞留和排序规则

工作：

- 按来稿时间计算等待天数；
- 初审使用90天阈值；
- 其他阶段按30、15、7天判断；
- 滞留标识由系统自动生成；
- 首页排序和独立红色预警区域正确。

完成标准：用边界日期测试时，未达到阈值、刚好达到阈值、超过阈值三种情况均符合规则。

### 第7天：完成删除保护、筛选和异常处理

工作：

- 删除项目必须二次确认；
- 增加按责任编辑、校对负责人、阶段和状态的基本筛选；
- 必填项缺失时给出清楚提示；
- 不允许重复开始、重复结束或跳过错误节点。

完成标准：常见误操作不会破坏流程数据。

### 第8天：安全、备份和恢复

工作：

- 检查 API Key、配置文件和数据库不会上传到 GitHub；
- 确认 GitHub 仓库为私人仓库；
- 设计手动备份方法；
- 实际做一次备份；
- 用备份恢复一次测试数据；
- 把步骤写入部署与备份说明。

完成标准：不仅能备份，还已经验证备份确实可以恢复。

### 第9天：完整验收和界面调整

工作：

- 按真实工作顺序走完多个测试项目；
- 测试不同流程组合；
- 测试三种稿件等级；
- 测试初审特殊阈值；
- 测试项目修改和删除；
- 记录问题，逐个修复；
- 只做影响使用的界面优化，不临时增加大功能。

完成标准：测试验收记录中，所有核心场景通过，严重问题为零。

### 第10天：领导演示和交付准备

工作：

- 准备6至10条模拟项目；
- 准备一条正常项目、一条急稿、一条重要急稿和一条滞留项目；
- 准备三分钟演示路线；
- 完成使用说明；
- 保存稳定版本；
- 列出“演示版已完成”和“内部试用前待完成”两张清单。

完成标准：不依赖开发人员解释技术，能够完整展示新建项目、推进流程、查看状态和发现滞留四个核心价值。

## 九、每次让 DeepSeek 工作时的固定格式

每次只发一个任务，固定写清以下内容：

1. 当前阶段；
2. 本次只完成的一个目标；
3. 必须读取的文档；
4. 不允许修改的范围；
5. 业务规则；
6. 完成后如何验证；
7. 要求说明修改了哪些文件；
8. 要求先检查现有实现，不重复创建已有内容。

推荐任务模板：

> 当前进行第X天、第X阶段。本次只完成“某一项功能”。请先读取指定文档和现有相关文件，再说明你的修改计划。必须遵守已确认的业务规则，不更换技术栈，不删除已有功能，不处理下一阶段内容。完成后请列出修改文件、运行方法、测试步骤和仍存在的问题。如果发现需求冲突，先停下说明，不要自行猜测。

如果 DeepSeek 一次返回大量修改，应先让它缩小范围；如果运行报错，只提供完整报错、相关页面截图和刚刚做过的操作，不要让它重新生成整个项目。

## 十、测试验收清单

第一版至少验证：

- 能创建、查看、修改和删除项目；
- 每本书能选择不同流程组合；
- 开始节点会记录开始时间；
- 结束节点会记录完成时间并进入下一节点；
- 最后节点结束后项目完成；
- 首页卡片字段和颜色正确；
- 重要急稿、急稿、普通稿排序正确；
- 同等级按收到时间排序正确；
- 初审90天规则正确；
- 其他阶段30、15、7天规则正确；
- 滞留项目同时出现在正常区域和红色预警区；
- 重启系统后数据仍存在；
- 数据库可以备份和恢复；
- 删除前有确认；
- 真实数据、数据库和密钥没有进入公共仓库或大模型对话。

## 十一、数据安全底线

1. 开发和演示阶段只使用虚构数据；
2. 不把真实未出版书名、作者信息、稿件内容或人员敏感信息发送给任何云端大模型；
3. DeepSeek 和 ChatGPT 中需要举例时，统一使用《测试图书A》、编辑甲、校对员乙等模拟内容；
4. API Key 只放在本机受保护配置中，不写入文档、不截图、不提交 GitHub；
5. GitHub 仓库保持私人；
6. SQLite 数据库文件不提交代码仓库；
7. 正式试用前完成登录、基本权限和单位批准的部署方案；
8. 定期执行备份，并定期验证恢复。

## 十二、现在应该做的第一步

暂时不要让 DeepSeek 开始生成整个系统。

先在 VS Code 中打开真正的项目根目录，把本文件放入 docs 文件夹，然后使用“第1天”的分析任务，让 DeepSeek只检查：

- 当前项目里已经有什么；
- 是否能够正常启动；
- 资料中的规则是否已经体现在当前文件中；
- 下一项最小开发任务是什么。

得到分析结果后，再决定从第2天开始，还是先修复现有项目环境。整个制作过程中始终坚持“一次一个小任务、运行通过后再进入下一步”。
